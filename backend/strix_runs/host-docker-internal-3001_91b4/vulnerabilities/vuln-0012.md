# Open redirect in /redirect via substring-based allowlist bypass

**ID:** vuln-0012
**Severity:** MEDIUM
**Found:** 2026-09-11 20:00:12 UTC
**Target:** http://host.docker.internal:3001
**Method:** GET
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The `/redirect` endpoint validates the `to` parameter against a URL allowlist using a substring (`includes`) check instead of exact matching. Any URL that embeds an allowlisted string anywhere — for example as userinfo credentials — passes validation, producing a 302 redirect to an attacker-controlled host.

## Evidence

Validated bypass (302 to attacker host via userinfo): `curl -i "http://host.docker.internal:3001/redirect?to=https://github.com/juice-shop/juice-shop@evil.com"` → `HTTP/1.1 302 Found` / `Location: https://github.com/juice-shop/juice-shop@evil.com` (browser navigates to host `evil.com`). Same technique with `https://blockchain.info/address/1AbKfgvw9psQ41NbLi8kufDQTezwG8DRZm/../../../evil` also returned 302. Control test: `curl "http://host.docker.internal:3001/redirect?to=http://example.com"` → `406 Not Acceptable`, `Error: Unrecognized target URL for redirect: http://example.com`. Enumerated allowlisted entries (each 302 with exact suffix passthrough): `https://github.com/juice-shop/juice-shop`, `https://blockchain.info/address/1AbKfgvw9psQ41NbLi8kufDQTezwG8DRZm`, `https://explorer.dash.org/address/Xr556RzuwX6hg5EGpkybbv5RanJoZN17kW`, `https://etherscan.io/address/0x0f933ab9fcaaa782d0279c300d73750e1311eae6`.

## Impact

An attacker can craft a link on the trusted application origin (e.g. `/redirect?to=https://github.com/juice-shop/juice-shop@evil.com`) that silently lands victims on an arbitrary external site, enabling credential phishing and token interception while the browser address bar initially shows the trusted origin. In this instance the impact is phishing/brand abuse only (no OAuth/redirect_uri flow was observed consuming this endpoint).

## Counterevidence

Checked alternatives that fail: arbitrary unknown URLs (http://example.com) correctly return 406 "Unrecognized target URL"; protocol-relative `//evil.com`, backslash `/\evil.com`, case tricks, scheme-less, and http-variant forms are all rejected; `javascript:` and `data:` schemes are rejected; subdomain trick (github.com/juice-shop.juice-shop.evil.com) rejected. No CSP or user-confirmation interstitial mitigates navigation to the redirected target. The only constraint found is the allowlist itself, and the substring-match flaw defeats it; no WAF or rate limiting observed on this endpoint.

## What Would Change This Severity

Discovery that any OAuth/OIDC or post-login flow trusts this endpoint as its redirect target would raise severity; conversely no such flow was found (severity would drop to informational).

## Technical Analysis

The redirect handler resolves the target via an allowlist check implemented as `allowed = allowed || url.includes(allowedUrl)` over a fixed set of allowlisted URLs (e.g. `https://github.com/juice-shop/juice-shop`, `https://blockchain.info/address/1AbKfgvw9psQ41NbLi8kufDQTezwG8DRZm`). Because a substring anywhere in the candidate URL satisfies the check, the userinfo URL form `https://<allowlisted-url>@<attacker-host>` passes validation. The handler then issues `res.redirect(toUrl)`, emitting the attacker-controlled URL in the `Location` header. Browsers ignore the userinfo component when resolving the host, so a victim following the redirect lands on the attacker's server. Path-traversal suffixes and query/fragment suffixes on allowlisted entries are likewise accepted (the full string is reflected in `Location`), confirming the validator checks containment rather than equality.

## Proof of Concept

1. Send `GET /redirect?to=https://github.com/juice-shop/juice-shop@evil.com` to the application. 2. Observe `HTTP/1.1 302 Found` with `Location: https://github.com/juice-shop/juice-shop@evil.com`. 3. Open the same URL in a browser: the userinfo portion is ignored for host resolution and the browser navigates to `evil.com`. 4. Any allowlisted entry works as the embedded string; e.g. `to=https://blockchain.info/address/1AbKfgvw9psQ41NbLi8kufDQTezwG8DRZm/../../../evil` also produces a 302 outside the allowlist intent. 5. Control case: `to=http://example.com` (no embedded allowlisted string) is correctly rejected with 406 "Unrecognized target URL".

```python
import requests

BASE = "http://host.docker.internal:3001/redirect?to="

# control: unlisted host is rejected
r = requests.get(BASE + "http://example.com", allow_redirects=False)
print("control:", r.status_code)  # 406

# bypass: allowlisted URL embedded as userinfo credentials
bypass = "https://github.com/juice-shop/juice-shop@evil.com"
r = requests.get(BASE + bypass, allow_redirects=False)
print("bypass:", r.status_code, r.headers.get("Location"))
# -> 302, Location: https://github.com/juice-shop/juice-shop@evil.com
# A browser following this Location navigates to host evil.com.
```

## Remediation

Replace the substring check with exact-match validation: parse the `to` parameter with a single URL parser and require the full URL to exactly equal one allowlisted entry (or to match an exact scheme + host + path-prefix allowlist after canonicalization). Reject any URL containing userinfo (`@` in the authority component), and treat query/fragment differences as mismatches.

## Assumptions

Assumes a victim can be induced to click an attacker-crafted link on the trusted application origin; no authentication required for the redirect endpoint itself.
