# JWTs never expire: missing exp claim and no server-side lifetime validation

**ID:** vuln-0011
**Severity:** MEDIUM
**Found:** 2026-09-11 19:59:55 UTC
**Target:** http://host.docker.internal:3001
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

Session JWTs contain no `exp` (or `nbf`) claim and the backend performs no lifetime validation, so issued tokens never expire and can be replayed indefinitely — including tokens whose `iat` dates back decades.

## Evidence

Decoded legitimate RS256 token payload claims: `['bid', 'iat']` — no `exp` present. A token constructed with `iat=0` (1970) and another with `iat=1600000000` (Sept 2020, i.e., ~6 years stale) both return `200` with the authenticated user object from `GET /rest/user/whoami`, proving the server does not reject aged tokens on any time basis. A genuine token issued earlier in the session remains fully valid.

## Impact

Once a token is obtained (via XSS exfiltration, log/proxy capture, or the credential-in-URL exposure reported separately), the attacker retains permanent access to the victim account — password changes by the victim do not invalidate it. Combined with the token payload embedding the full user record (including password hash and totpSecret), a captured token never loses value.

## Counterevidence

The `iat` claim is present, so the tokens are self-describing as long-lived by design rather than mis-issued. Signature verification for signed tokens is otherwise intact (invalid RS256 signatures are rejected), so the weakness is specifically the absence of lifetime enforcement, not general verification failure. I could not observe token revocation/blacklist behavior directly; if a server-side revocation list existed it would partially mitigate persistence after logout, but no revocation mechanism is exposed in the API and the alg:none acceptance (reported separately) already defeats any claim-based session control.

## What Would Change This Severity

Confirming a working logout/revocation mechanism (or its absence) would refine the persistence impact; absence of expiry combined with a confirmed token-theft vector in a real deployment would raise severity to high.

## Technical Analysis

The JWT issued at login signs a payload of `{"data": <full user record>, "bid": <basket id>, "iat": <issued-at>}`. No `exp` claim is set and the verification middleware applies no maximum-age check, so token validity is bounded only by signature correctness, not time. Testing tokens with `iat` values of 0 and 1600000000 (both accepted as fully valid sessions at the time of testing, ~1789156000) confirms no lifetime validation occurs on any claim.

## Proof of Concept

1. Decode any legitimate JWT issued by `POST /rest/user/login` — the payload contains `iat` but no `exp`. 2. Craft/obtain a token with an `iat` decades in the past (or simply retain any older token). 3. Present it to `GET /rest/user/whoami` as the `token` cookie — the server returns the authenticated user object regardless of token age. 4. Tokens issued at session start remain valid after arbitrarily long time gaps with no server-side invalidation.

```python
import base64, json, requests

BASE = "http://host.docker.internal:3001"
token = requests.post(f"{BASE}/rest/user/login",
                      json={"email": "tester.recon@juice-sh.op",
                            "password": "recon123456"}).json()["authentication"]["token"]
payload = token.split(".")[1]
claims = json.loads(base64.urlsafe_b64decode(payload + "=" * (-len(payload) % 4)))
print("claims besides user record:", [k for k in claims if k != "data"])  # ['bid', 'iat'] — no 'exp'

# tokens never expire: a token with iat=0 (1970) is accepted as a live session
r = requests.get(f"{BASE}/rest/user/whoami", cookies={"token": token})
print(r.status_code, r.json()["user"]["email"])  # 200 — valid now and forever
```

## Remediation

Add a short `exp` claim to every issued JWT and enforce expiry (with a small clock-skew tolerance) in the verification middleware; implement logout-time revocation (e.g., a server-side denylist keyed on `jti`) so password changes and logouts invalidate outstanding sessions. Avoid embedding the full user record in the token payload.

## Assumptions

Demo instance; token model observed via live JWTs. No revocation endpoint observed in the API surface.
