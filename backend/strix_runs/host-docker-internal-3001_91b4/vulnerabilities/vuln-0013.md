# Reflected DOM XSS via q parameter on search results page

**ID:** vuln-0013
**Severity:** MEDIUM
**Found:** 2026-09-11 20:00:28 UTC
**Target:** http://host.docker.internal:3001
**Method:** GET
**CWE:** CWE-79
**CVSS:** 5.4
**Confidence:** High
**Fix Effort:** Low

## Description

The `q` query parameter on the search results page is passed unsanitized through `sanitizer.bypassSecurityTrustHtml()` and rendered via Angular `[innerHTML]`, allowing arbitrary script execution in any victim's browser when they follow an attacker-crafted link.

## Evidence

Browser session opened `http://host.docker.internal:3001/#/search?q=%3Cimg%20src%3D1%20onerror%3D%22window.__XSS_SEARCH%3D%27EXEC%27%22%3E`; after load, `window.__XSS_SEARCH` evaluated to `"EXEC"` — the injected `onerror` handler executed. Separately, `?q=<iframe src="javascript:alert(`xss`)"></iframe>` produced a live iframe element in the DOM (`<iframe src="javascript:alert(`xss)"></iframe>` via querySelector). Bundle source: `this.searchValue=this.sanitizer.bypassSecurityTrustHtml(e)` in the search-result component's `filterTable()`.

## Impact

An attacker can craft a link that executes arbitrary JavaScript in any Juice Shop user's browser. Juice Shop stores its JWT in a `token` cookie readable via same-origin script, enabling session theft, account takeover, unauthorized purchases, and defacement of the victim's view. Requires the victim to click a link.

## Counterevidence

Tested for mitigations: no Content-Security-Policy header is present on responses (only X-Frame-Options and Feature-Policy), the Angular sanitizer is explicitly bypassed by the component's own bypassSecurityTrustHtml call, and no validation of q occurs before render. The iframe/javascript: variant renders as a live DOM element; the img+onerror variant executes script. No blocking control found.

## What Would Change This Severity

A strict CSP (no unsafe-inline, no javascript: sources) would block execution and lower this to informational; confirmation of a stored variant on any other [innerHTML] sink would raise severity to high.

## Technical Analysis

The search-result component's `filterTable()` reads `this.route.snapshot.queryParams.q`, then executes `this.searchValue = this.sanitizer.bypassSecurityTrustHtml(e)` and binds `searchValue` in the template via `[innerHTML]`. `bypassSecurityTrustHtml` disables Angular's contextual sanitization, so the raw attacker-controlled query string is inserted as live HTML. HTML-parser-observable payloads (e.g. `img src=x onerror=...`) execute JavaScript; `<iframe src="javascript:alert(\`xss\`)">` renders an iframe with a javascript: source. The value never leaves the browser (pure DOM sink), so no server-side sanitizer touches it.

## Proof of Concept

1. Open the URL `http://host.docker.internal:3001/#/search?q=%3Cimg%20src%3D1%20onerror%3D%22window.__XSS_SEARCH%3D%27EXEC%27%22%3E` in a browser.
2. After the search results page loads, evaluate `window.__XSS_SEARCH` in the console — it returns "EXEC", proving the injected onerror handler executed.
3. Alternatively, the classic `?q=<iframe src="javascript:alert(`xss`)"></iframe>` renders a live iframe with a javascript: source in the page DOM.

## Remediation

Remove the `bypassSecurityTrustHtml` call on the search query value and render it as plain interpolated text instead of `[innerHTML]`, so Angular's default contextual escaping applies. If rich rendering is genuinely required, run the value through DOMPurify before binding, and add a Content-Security-Policy header without `unsafe-inline` as a second layer of defense.

## Assumptions

Victim must follow an attacker-supplied link to the search page (standard reflected-XSS prerequisite). No authentication required to reach the vulnerable page.
