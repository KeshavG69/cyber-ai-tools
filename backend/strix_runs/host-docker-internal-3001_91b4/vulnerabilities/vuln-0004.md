# IDOR: Any authenticated user can read any other user's shopping basket (GET /rest/basket/:id)

**ID:** vuln-0004
**Severity:** MEDIUM
**Found:** 2026-09-11 19:56:30 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /rest/basket/:id
**Method:** GET
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The `GET /rest/basket/:id` endpoint returns any user's shopping basket to any authenticated customer. The server validates the JWT but never checks that the requested basket ID belongs to the token's user, allowing a logged-in customer to enumerate and read every other user's basket, including current product selections, quantities, and prices.

## Evidence

Attacker (user A, id 25) requesting user B's basket (id 7):

```json
GET /rest/basket/7
Authorization: Bearer <A's customer JWT>

200 OK
{"status":"success","data":{"id":7,"coupon":null,"UserId":27,"Products":[{"id":3,"name":"Eggfruit Juice (500ml)","price":8.99,"BasketItem":{"quantity":1}}]}}
```

Same request without a token: `401 UnauthorizedError`. Baskets 1-7 all returned 200 with their owners' contents (e.g. basket 2 → UserId 2 with Raspberry Juice). Owner-only control request `GET /rest/basket/6` returns A's own empty basket, confirming the ID is the only differentiator.

## Impact

Any registered customer can enumerate baskets 1..N and read every other user's shopping activity in real time: which products they intend to buy, quantities, and prices. This is a direct disclosure of other users' purchase-intent data (business-confidential in a real shop) with trivially guessable integer IDs.

## Counterevidence

Checked whether the route is simply public: an unauthenticated request returns 401, so authentication is enforced but object-level authorization is not. Checked whether the response was cached or stale by comparing live edits (item added by B appears immediately in A's read). Checked whether only baskets without an owner were returned: response includes UserId 27 and the exact items B just added. No ownership control found on this path.

## What Would Change This Severity

If baskets were found to also expose stored delivery addresses or payment details, confidentiality impact would rise to High.

## Technical Analysis

`GET /rest/basket/:id` resolves the basket by the raw path parameter. The route sits behind JWT authentication middleware, but the handler performs no comparison between the path ID and the `bid`/`data.id` claims embedded in the token. Basket IDs are small sequential integers (1, 2, 3...), so enumeration is trivial. The authentication middleware only proves the caller is *a* user, not *the* basket's owner — the object-level authorization step (CWE-639) is entirely absent. Unauthenticated requests are correctly rejected, which confirms the missing control is ownership, not authentication.

## Proof of Concept

1. Register two accounts (attacker A, victim B) and log in as each to obtain JWTs. 2. As B, add a product to B's basket via `POST /api/BasketItems` and note B's basket ID from the login response (`bid`). 3. Send `GET /rest/basket/<B's basket id>` with A's JWT in the `Authorization: Bearer` header. 4. Observe a 200 response containing B's basket: `UserId` of B, and the exact product and quantity B added. 5. Confirm the same request without a token returns 401, proving the flaw is ownership, not authentication.

```python
import requests

BASE = "http://host.docker.internal:3001"

a_login = requests.post(BASE + "/rest/user/login", json={
    "email": "tester.recon@juice-sh.op", "password": "recon123456"}).json()["authentication"]["token"]
b_login = requests.post(BASE + "/rest/user/login", json={
    "email": "idor.b.jcgpw4pc@juice-sh.op", "password": "IdorTest123!"}).json()["authentication"]
b_basket_id = b_login["bid"]
requests.post(BASE + "/api/BasketItems",
              headers={"Authorization": "Bearer " + b_login["token"]},
              json={"BasketId": b_basket_id, "ProductId": 1, "quantity": 2})

# Attacker reads victim's basket with the attacker's own token
r = requests.get(f"{BASE}/rest/basket/{b_basket_id}",
                 headers={"Authorization": "Bearer " + a_login})
print(r.status_code, r.json()["data"]["UserId"],
      [(p["name"], p["BasketItem"]["quantity"]) for p in r.json()["data"]["Products"]])
# -> 200 27 [('Apple Juice (1000ml)', 2)]  : victim's UserId and basket contents leaked

print(requests.get(f"{BASE}/rest/basket/{b_basket_id}").status_code)  # -> 401 without any token
```

## Remediation

Bind the basket lookup to the authenticated principal: after JWT validation, derive the basket ID from the token's `bid` claim (as the application already does for the caller's own basket) or, when an explicit ID is accepted, query with a `where` clause on both the requested basket ID and the token user's ID, returning a 403/404 on mismatch. Do not rely on the client to pass its own basket ID.

## Assumptions

Assumes the attacker holds any valid customer JWT, obtainable by free self-registration. Demo instance with seeded data; real deployment would expose genuine customer purchase-intent data.
