# Password change via GET with credentials in URL query string, response discloses password hash

**ID:** vuln-0010
**Severity:** MEDIUM
**Found:** 2026-09-11 19:59:30 UTC
**Target:** http://host.docker.internal:3001
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The password-change operation is performed via `GET /rest/user/change-password` with the current and new passwords transmitted as URL query-string parameters, causing credentials to be stored in browser history, proxy logs, and server access logs. The successful response additionally returns the user's full record including the (unsalted MD5) password hash.

## Evidence

`GET /rest/user/change-password?current=AuthSpec123!&new=TestHash99!&repeat=TestHash99!` with a valid Bearer token returns `200` with body `{"user":{...,"password":"8dc871f953ec1d007d82e50de66b07cf",...}}` — the hash matches `md5("TestHash99!")` exactly, proving the response discloses the freshly set password hash and that hashing is unsalted MD5. The SPA client bundle itself constructs this URL (`/rest/user/change-password?current=`+e.current+`&new=`+e.new).

## Impact

Current and new passwords persist in cleartext in URL-based log stores (browser history, proxies, referer headers, server access logs), which in a real deployment exposes user credentials to anyone with log access. The response hash disclosure (plus unsalted MD5 password storage) enables offline cracking of the user's password. No cross-user modification was demonstrated; the attacker must already hold a valid session token for this account.

## Counterevidence

Actively tested the CSRF angle: when the token is supplied via the `token` cookie (the browser-authenticatable channel), the endpoint refuses with `Error: Blocked illegal activity` and header IP spoofing (X-Forwarded-For, True-Client-IP, X-Origin-IP) does not bypass the block — so a cross-site CSRF attack via `<img src=...>` would fail on a cookie-authenticated session. The weakness that remains is the GET method with credentials in the URL and the verification being bypassable by attacker-controlled header/URL logging, not a direct CSRF exploit. Authorization is enforced (wrong current password returns 401; unauthenticated calls are blocked).

## What Would Change This Severity

Demonstrating log/history access capturing these URLs in a real deployment would confirm the credential-exposure impact and could raise severity; the hash-disclosure component would drop out if the response stopped embedding the user record.

## Technical Analysis

The Angular SPA calls `GET /rest/user/change-password?current=<pwd>&new=<pwd>&repeat=<pwd>` (visible in the main.js bundle). The handler verifies the current password, updates the record, and returns the full updated Sequelize user object — which includes the `password` attribute (an unsalted MD5 hex digest, confirmed by comparing the returned hash to `md5()` of the new password) — directly in the JSON response. Because it is a GET with a query string, both the old and new passwords are persisted in any URL-recording layer.

## Proof of Concept

1. Log in to obtain a valid JWT. 2. Send `GET /rest/user/change-password?current=<current>&new=<new>&repeat=<new>` with the token as `Authorization: Bearer`. 3. Observe a 200 response whose `user` object contains the account record including the new password hash (unsalted MD5). 4. Note that the credentials traveled fully in the request URL, which is recorded in browser/proxy/server logs.

```python
import hashlib, requests

BASE = "http://host.docker.internal:3001"
token = requests.post(f"{BASE}/rest/user/login",
                      json={"email": "auth.spec.massadm@juice-sh.op",
                            "password": "AuthSpec123!"}).json()["authentication"]["token"]

r = requests.get(
    f"{BASE}/rest/user/change-password?current=AuthSpec123!&new=TestHash99!&repeat=TestHash99!",
    headers={"Authorization": f"Bearer {token}"},
)
user = r.json()["user"]
print("status:", r.status_code)
print("hash in response:", user["password"])
print("md5 of new password:", hashlib.md5(b"TestHash99!").hexdigest())
assert user["password"] == hashlib.md5(b"TestHash99!").hexdigest()
# credentials traveled entirely in the URL query string
```

## Remediation

Move the password-change operation to a `POST`/`PUT` endpoint with credentials in the request body over TLS; never place passwords in URLs. Stop returning the password hash (or any password-derived value) in API responses, and replace unsalted MD5 password hashing with a dedicated password hash such as bcrypt, scrypt, or Argon2.

## Assumptions

Authenticated account holder; demo instance.
