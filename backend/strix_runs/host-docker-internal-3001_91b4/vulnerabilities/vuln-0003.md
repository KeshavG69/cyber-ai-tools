# Unauthenticated user enumeration and security-question disclosure via /rest/user/security-question

**ID:** vuln-0003
**Severity:** MEDIUM
**Found:** 2026-09-11 19:56:12 UTC
**Target:** http://host.docker.internal:3001
**CVSS:** 5.3
**Confidence:** High
**Fix Effort:** Low

## Description

The unauthenticated security-question lookup endpoint discloses which email addresses are registered (full question object vs empty object) and returns the account's configured security question, providing a username-enumeration oracle and reconnaissance for targeted password-reset attacks.

## Evidence

`GET /rest/user/security-question?email=admin@juice-sh.op` → `200 {"question":{"id":2,"question":"Mother's maiden name?",...}}`. `GET /rest/user/security-question?email=nosuchuser@juice-sh.op` → `200 {}`. The differential is deterministic across repeated calls. The reset endpoint `POST /rest/user/reset-password` returns a separate distinguishable error (`Wrong answer to security question.`) confirming the live verification oracle.

## Impact

Any anonymous attacker can reliably enumerate registered accounts and obtain each account's security question, focusing brute-force and phishing attacks on real users; the question text materially aids guessing the answer for the password-reset flow. On this instance, 28+ seeded accounts are confirmable within seconds. No direct data compromise beyond account existence and question disclosure was demonstrated.

## Counterevidence

Actively attempted to escalate this into a working account takeover: guessed the seeded admin's security answer from Juice Shop lore (25+ candidate answers from known seeded-account lore), and — via admin access obtained through the separate mass-assignment flaw — dumped the SHA-256-hashed security answers and attempted offline recovery of the admin's hash against 1M+ password and name wordlists, all without success. Reset-password type confusion (array/object/null/boolean answers) was also rejected. The answer hash being stored as an unsalted SHA-256 makes offline cracking plausible in principle, but no plaintext was recovered in this run, so the demonstrated impact remains account enumeration plus verification oracle. The endpoint also returns the configured security question to anonymous callers, which is itself a prerequisite information leak.

## What Would Change This Severity

Recovering any seeded account's security-answer plaintext (enabling the full password-reset takeover) would raise this to high; adding a uniform response would remediate the enumeration entirely.

## Technical Analysis

The handler for `GET /rest/user/security-question` looks up the user by email and, when found, returns the associated security question record; when not found it returns an empty JSON object. It is unauthenticated and performs no rate limiting or response normalization, so the two outcomes are trivially distinguishable. The question content additionally arms an attacker for the `POST /rest/user/reset-password` flow, which verifies the answer against a SHA-256 hash stored in the `SecurityAnswers` table.

## Proof of Concept

1. Send `GET /rest/user/security-question?email=admin@juice-sh.op` unauthenticated — the response contains the full security-question object for that account. 2. Send the same request with a random nonexistent email — the response is an empty object `{}`. 3. The differential confirms account existence and leaks the account's security question, which is the first stage of the password-reset flow.

```python
import requests

BASE = "http://host.docker.internal:3001"

existing = requests.get(f"{BASE}/rest/user/security-question",
                        params={"email": "admin@juice-sh.op"}).json()
nonexistent = requests.get(f"{BASE}/rest/user/security-question",
                           params={"email": "nosuchuser@juice-sh.op"}).json()
print(existing)    # {"question": {"id": 2, "question": "Mother's maiden name?", ...}}  -> account exists
print(nonexistent) # {}                                                                   -> account does not
```

## Remediation

Return a generic, identical response (e.g., an empty object or a neutral message) regardless of whether the email exists; never disclose the configured security question until the user has proven control of the account through a different channel (e.g., emailed reset link), and rate-limit the lookup.

## Assumptions

Demo instance with seeded accounts; no authentication required.
